日期：2026-10-03。产品源码核验基线为 `2073ae74747431aab8d529803d4e9f8197262388`，包版本 `2.5.0`；首版文档提交为 `86d5a17`。

## 审阅目标与证据范围

Red-teaming 在本记录中表示主动挑战文档断言：寻找未覆盖调用方、被省略的状态、参数丢失、恢复时序和测试装配差异。
目标是让后续 agent 找到正确修改边界，避免把局部能力理解成全链路保证。

六个独立审阅任务从新上下文读取 AGENTS、指南入口及指定专题，再沿链接核对实际源码和测试定义。审阅者未参与相应文档的编写，未读取旧本地指南、交接或真实凭据及样本。
审阅使用假设故障场景和源码控制流推导，没有执行产品测试、模型请求、故障注入、浏览器或网络操作。

每项反馈必须包含原文、源码符号或分支、能推翻原表述的反例、最小文档修订及尚未验证的事实。
作者的自查限制不计入独立审阅发现数。修订后由原审阅者定点复查；最后又同步了调用图、反例说明和正文之间的剩余差异。

## 实现风险与文档缺陷分别处理

本轮修正的是知识描述和修改导航。G-01 至 G-07 保留在[证据与差异登记](evidence-and-drift.md)，其他领域限制在各专题的源码与反例段落保留。
静态代码可以证明某个检查缺失或某个异常能够跳过后续语句，但通常仍需要可控复现才能确认真实环境中的用户后果。

后续产品修复应按独立任务固定触发条件与预期结果。下面几类证据尤其不能互相替代：

- `writebackCancellationFlow` 的 router 直接测试不能证明 broker 回执取消后 content 获得了 checkpoint。
- 用成功 settlement stub 的 Undo 镜像测试不能证明中间保存失败也会执行镜像失效。
- 假 worker 与相同路径字符串的并发测试不能证明路径别名互斥或真实 OS 进程退出。
- 提供协议终止原因的工具调用测试不能证明正常 EOF 下半段 JSON 被拒绝。
- 片段提取测试额外注入的变量、stub 或全局状态可能与实际工厂装配不同。
- 流传输结果、原生回执和版本健康不能单独证明浏览器最终保存、恢复或业务功能成功。

这些边界用于帮助后续任务选择有意义的验证。它们不要求在每次文档维护中执行全部测试或真实故障注入。

## 可重复的改进步骤

1. 固定产品源码提交、文档起点和本轮范围，排除未提交候选与私人材料。
2. 为重要断言记录 owner、实际调用方、状态写入点和最近测试；主流程之外至少列取消、超时或恢复的相关分支。
3. 让未参与编写的 agent 只从新指南定位，再追踪参数、异步顺序及实际测试 harness。
4. 仅接收有源码证据的反例。已有明确限定的设计范围不重复计为新缺陷；没有反例也不等同全面安全认证。
5. 在同一轮修订正文、图、配方和反例题，避免章节之间继续互相矛盾。
6. 原审阅者定点复查；无法补足执行证据的项保留为待验证，实现问题另行修复。
7. 检查相对链接、符号、测试选择器、版本控制范围和私有资料忽略，再单独提交文档。

每轮以“本次已确认的文档问题已修订，未证实项已明确范围”为收口条件。后续代码变化或新的真实证据触发下一轮，不以反复生成意见的数量衡量质量。
