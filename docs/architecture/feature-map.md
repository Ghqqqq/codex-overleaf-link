# Feature Change Navigation

Initial reference product version: `2.5.0`; initial reference source baseline: `2073ae7`. This index is maintained alongside the current repository; task execution and synchronization requirements are defined in the [development and repair SOP](change-workflow.md).
This page records entry points, state owners, required coordinated changes, and verification routes for the current implementation. An owner is the module with authority over a state or behavioral decision; the UI usually displays a projection of that state.

Start here: [Architecture guide home](README.md) · [System overview](system-overview.md).
Core flows: [Auto editing and Undo](auto-edit-undo.md), [Run state and recovery](run-state-and-recovery.md). Other domain pages expand the main paths and failure boundaries in the groups below; implementation changes still require checking the corresponding source.
Navigation method: first match the user's intended change, then follow “entry point → state owner → coordinated changes → verification”; symbol names can be used directly in source searches.
Verification entries below apply to the path being changed. They distinguish retained automated contracts from focused manual checks; they do not form a mandatory full release matrix.

## UI, Settings, and Diagnostics

Domain guide: [UI and loading](ui-and-loading.md).

### Change the panel entry point, width, or layout

- Entry points: [PanelRenderer.create](../../extension/src/content/panelRenderer.js); [ContentRuntime.ensurePanelOpen](../../extension/src/content/contentRuntime.js) assembles the slots.
- State owner: PanelRenderer manages the DOM and resizing; width enters runtime/prefs, while launcher visibility is stored separately in `chrome.storage.local['codex-overleaf:launcher-visible']`. Whether the panel is open is DOM state; initialization after a refresh reopens the panel.
- Required coordination: [panel.css](../../extension/styles/panel.css), [sessionState](../../extension/src/shared/sessionState.js); preserve the settings, session, and composer lifecycles.
- Header: the active session title is the switcher trigger ([SessionMenuView](../../extension/src/content/sessionMenuView.js)) with per-row deletion through `renderSessionMenu → deleteSessionWithConfirm`, and the diagnostics trigger carries a health label and the Refresh file status menu action; the Sessions list slot is hidden. See [header session switcher](ui-and-loading.md#header-session-switcher).
- Text sizes and colours: use the `--tl-text-*` scale and `--tl-*` colour tokens in [panel.css](../../extension/styles/panel.css); see [type scale and colour tokens](ui-and-loading.md#panel-type-scale).
- Verification: When changing this surface, open/close and resize the actual panel; verify its affected layout after refresh, in both themes.

### Change runtime activity, reading follow behavior, the latest button, or answer copying

- Entry points: [RunTimelineView.bindLogAutoFollow/scrollLogToBottom](../../extension/src/content/runTimelineView.js), `configureCopyButton` in [RunResultActions](../../extension/src/content/runResultActions.js).
- State owner: the timeline manages follow intent, unread steps, and forced jumps; [RunScrollLayout](../../extension/src/content/runScrollLayout.js) preserves the reading anchor before repaint. Copying uses the rendered answer text, excluding the run log and raw Markdown.
- Required coordination: streaming output, collapsing, repainting, font and width changes, the Clipboard API/fallback, and action failure notices. See [UI and loading](ui-and-loading.md) for details.
- Collapsed activity: [RunActivityModel.project](../../extension/src/shared/runActivityModel.js) combines saved events with incoming display snapshots by stream identity; [RunActivitySummary.renderPeek](../../extension/src/content/runActivitySummary.js) owns the three-row window. Coordinate runtime `appendRunEvent`/`upsertRunStreamRecordEvent`, session normalization, and the timeline's stream and elapsed-timer refreshes; see [activity projection](ui-and-loading.md#activity-projection-and-post-write-receipts).
- Verification: When changing this path, use a long answer to check manual scrolling, the latest button, and copied conclusion text.
- For activity-only changes, check that repeated updates of one Thinking stream preserve the three rows and their node identity, while a new stream can advance the window. Include current-record updates after session normalization, completion and history reconstruction; source-string and CSS assertions do not establish these behaviors.

### Add settings or change their categories or scope

- Entry points: [SettingsPanel.create/readState/loadState](../../extension/src/content/settingsPanel.js), [SettingsWorkbench.mount](../../extension/src/content/settingsWorkbench.js).
- State owners: global preferences go through [GlobalPreferencesController](../../extension/src/content/globalPreferencesController.js); project instructions and governance configuration go through [ProjectSettingsCoordinator](../../extension/src/content/projectSettingsCoordinator.js).
- Required coordination: field ownership in [globalPreferences](../../extension/src/shared/globalPreferences.js) and [sessionState](../../extension/src/shared/sessionState.js); the `SECTIONS/GROUP_PAGES` page mapping in [SettingsWorkbench](../../extension/src/content/settingsWorkbench.js), whose section also decides project availability. The workbench moves existing controls, preserving drafts and listeners. Section headings and rows use the workbench rules in [panel.css](../../extension/styles/panel.css); `refreshSoleSections` recomputes `data-sole-section` after visibility and locale refresh, and footer messages that belong to one category pass `{ page }` to `SettingsPanel.setStatus`, as described in [UI and Loading](ui-and-loading.md#2-panel-and-settings-dom-as-a-projection-of-state).
- Verification: When changing a setting, verify its intended account/project/global scope after reopening and refresh; inspect the affected failure path.

### Change answer Markdown, formulas, or file-line navigation

- Entry points: [MarkdownText.create](../../extension/src/content/markdownText.js), [MarkdownDomRenderer.renderMarkdown](../../extension/src/content/markdownDomRenderer.js).
- State owners: renderers manage the DOM; [lineReferences](../../extension/src/shared/lineReferences.js) parses single positions/ranges and resolves project paths, [textCoordinates.resolveJumpToPositionRange](../../extension/src/page/textCoordinates.js) owns line/column and inclusive `endLine` selection, and [MathText](../../extension/src/content/mathText.js) manages formula parsing and fallback.
- Required coordination: project file identity, `createLineReferenceButton` → [pageBridge.jumpToPosition](../../extension/src/pageBridge.js) parameter forwarding, [pageRpcContract.REVISION](../../extension/src/shared/pageRpcContract.js) for changed Page closures, [codexPromptAssembly.formatProjectLocationCitationRules](../../native-host/src/codexPromptAssembly.js), TeX macro sources, KaTeX/vendor loading, and web-accessible font resources; preserve disabled raw HTML, source display on formula failure, and local-path redaction. See [Rich Text, Math, and References](ui-and-loading.md#rich-text-math-and-references).
- Cross-file readiness: [pageBridge.waitForActiveEditorAfterNavigation](../../extension/src/pageBridge.js) requires a changed CodeMirror document, rather than only a changed view/state, before `jumpToPosition` resolves offsets. This check is specific to navigation; shared writeback/Undo identity checks remain separate.
- Verification: When changing rendering, inspect representative Markdown/math and a real single-line/range jump in Chrome, including the affected fallback, parenthesis grouping, invalid ranges, and end-line clamping. For cross-file navigation, verify the first click with both a range beyond the old document's length and one valid in both documents; focus/configuration changes alone must not make the old document ready.

- Closing results only establishes a display barrier; it does not cancel the original check. The Controller separately constrains late results and full-check health by request generation and account/project/route identity. Export captures the account/project and filters audit records; see [audit and diagnostic consumers](context-and-governance.md#5-audit-and-diagnostics-consumers) for legacy-field compatibility.
- Verification: When changing diagnostics, inspect the affected export or result under its captured account/project; check a late response after closing or replacing the result.

## Models, Selections, and Attachments

See [Providers and protocols](providers-and-protocols.md) for model execution and connections; see [UI and loading](ui-and-loading.md) for selection and input lifecycles.

### Change the model, Reasoning, Speed, or Provider selection

- Entry points: [ModelPicker.loadModelOptions](../../extension/src/content/modelPicker.js), [ProjectProviderSelection](../../extension/src/content/projectProviderSelection.js).
- State owners: [models](../../extension/src/shared/models.js) normalizes capabilities; [ProviderSettingsCoordinator](../../extension/src/content/providerSettingsCoordinator.js) coordinates configuration; project selection and submitted run snapshots are saved separately.
- Required coordination: [modelPickerSupport](../../extension/src/content/modelPickerSupport.js), [providerRuntime.resolveProviderModels](../../native-host/src/providerRuntime.js), [runExecutionSnapshot](../../extension/src/shared/runExecutionSnapshot.js); preserve the generation, providerId, and providerRevision guards against late responses.
- Shortcut entry points also require checking protocol/address/authentication coordination between [ProviderProfiles](../../extension/src/shared/providerProfiles.js) and the dialog; final Speed arguments are generated by [codexArgs.buildCodexSpeedArgs](../../native-host/src/codexArgs.js). The Native default Provider and the current project's selection are separate states; text shown after clearing a key or changing an endpoint cannot by itself prove that selection changed.
- If the issue concerns which configuration a queued task actually uses, follow `RunExecutionSnapshot.resolveForExecution` → `RunInputQueue.claimNext` → `RunQueueScheduler.scheduleOne` and check the pause branches, then inspect Native `providerRuntime.resolveRunProvider/resolveRunProviderForRun`; loading the model catalog does not replace execution validation.
- Verification: When changing selection, verify the actual submitted model/Provider and the affected delayed or failed catalog response. The core suite has no Provider-selection UI test.
- Selection protection during active runs connects to the Coordinator through `ProjectProviderSelection.assertSwitchAllowed/commit`; checks continue before repainting an asynchronous model catalog, while configuration saving and project selection remain separately managed. A failed current model request is classified as stale only by its actual generation/identity; a missing revision in an error packet does not automatically make it a late result.

### Change Context Usage or the Compact Status

- Entry points: [contentRuntime.appendNativeEvent/renderContextUsage/getContextUsageDisplay/getCompactAvailability](../../extension/src/content/contentRuntime.js), [ContextUsageView.create](../../extension/src/content/contextUsageView.js), and the icon-only model-adjacent pie in [ComposerPanel](../../extension/src/content/composerPanel.js).
- State owner: [ContextUsage](../../extension/src/shared/contextUsage.js) validates the latest parent-thread report; session/run snapshots retain its model and Provider revision. `status` separates `pending` (the old sample is invalid) from `compacted` (the latest invalidating compaction has completion evidence). Failed, cancelled and interrupted attempts can withhold old usage without claiming success. `level` defines the 70%/90% presentation thresholds shared by the indicator and the `/compact` menu tag. Latest response totals and cumulative usage have different meanings. Capacity comes from the report, with unknown values kept unknown. The popover's input/output shares use the latest reported input plus output; cached input is a subset with a separate same-response cache hit rate.
- Required coordination: [SessionState](../../extension/src/shared/sessionState.js), [StorageDb](../../extension/src/shared/storageDb.js), runtime hydration, model-picker redraws, Provider/thread replacement and fork isolation. See [context usage](ui-and-loading.md#context-usage-beside-the-model) for selection and display rules.
- Compact lifecycle: [RunActivityModel.contextCompactionState/capture/project/getCompactedAt](../../extension/src/shared/runActivityModel.js) is shared by [AgentTranscript](../../extension/src/shared/agentTranscript.js), [RunActivitySummary](../../extension/src/content/runActivitySummary.js), and the runtime indicator. [codexSessionRunner.inferNotificationStatus](../../native-host/src/codexSessionRunner.js) treats legacy `thread/compacted` as completed. Preserve modern item identity and clear the display at completion/cancellation without adding rows. `project(run).compactedAt` drives the automatic-compaction divider (`RunActivitySummary.renderCompaction`). Runtime uses `getCompactedAt` across all retained non-fork normal runs in the same thread to keep older samples withheld when another turn starts.
- Automatic-compaction decisions belong to the CLI. For a rejected Chat request, inspect both structured image translation and the Responses context-limit failure event; changing indicator thresholds does not alter that decision. The recognized overflow can enable compaction on the next turn while the current turn still fails. See [Provider conversion](providers-and-protocols.md#61-streaming-buffered-responses-and-tool-calls).
- Manual command: runtime `getSlashCommands/selectSlashCommand/safeRunTask/runTask` routes `/compact` through `codex.run` with `operation: compact`; the popover's Compact action enters the same `safeRunTask`. Only exact command submission or slash-menu selection requests `consumeCompactDraft`; the popover preserves every draft, including slash-prefixed text. `RunActivitySummary.mountCompaction/renderCompaction` render the compact run card as a tag plus a status divider. [taskRunnerRuntime.handleCodexRun](../../native-host/src/taskRunnerRuntime.js) and [codexSessionRunner.runCodexSession/runCodexAppServerProcess](../../native-host/src/codexSessionRunner.js) retain the original thread and run locks, skip document work, and await completion after `thread/compact/start`. Check the optional `threadCompact` capability, no-new-thread fallback, non-steerable state, persisted operation and journal recovery together.
- Verification: extend the existing [sessionDurability](../../test/sessionDurability.test.js) contract for persisted snapshots. Use a short live check for actual usage delivery, locale changes, model/session switching and the compact header; temporary lifecycle/DOM probes can verify start/completion and the unchanged three-row window without forcing a costly real compaction.

### Change Ask/Auto, send controls, or Edit Selection

- Entry points: [ComposerPanel.create](../../extension/src/content/composerPanel.js), [SelectionContextView.attach](../../extension/src/content/selectionContextView.js), runtime `safeRunTask`.
- State owners: [sessionState](../../extension/src/shared/sessionState.js) stores drafts; [selectionContext](../../extension/src/shared/selectionContext.js) normalizes selections; selection context enters the execution snapshot on submission.
- Required coordination: [pageBridge.getSelectionContext](../../extension/src/pageBridge.js), [Native selectionScope](../../native-host/src/selectionScope.js), [runExecutionSnapshot](../../extension/src/shared/runExecutionSnapshot.js). Only Ask/Auto are currently supported, with Ask as the default; legacy `confirm` normalizes to Ask.
- Edit Selection admission checks whole-document identity and permits rebasing only with unambiguous evidence. `filterSelectionChanges` evaluates each collected item: an independently valid write to the selected file can proceed while out-of-scope items are withheld. A collected write that also changes text outside the selection is withheld as a whole; if multiple entries target the selected path, all of those entries are withheld. When no valid writes remain, the existing blocked-result path applies.
- Verification: When changing submission or selection editing, verify the captured mode/range and a rejected out-of-range edit in a disposable project.

- Required coordination: the existing save queue and primary-commit acknowledgement, `SessionManager.startNewSession/switchSession`, non-queued `runTask` submission, update-idle storage checks, hidden/pagehide best-effort flushing, and the departing-route `saveState({draftScope})` detached save. When this path changes, also check composition commit, draft recovery/switching, and typing during a running stream through the actual runtime; lifecycle delivery and a completed durable write are separate evidence.

### Change @file context, pasted/dropped attachments, or attachment limits

- Entry points: [ContextTray](../../extension/src/content/contextTray.js), [ComposerAttachments.createComposerAttachmentController](../../extension/src/content/composerAttachments.js).

- Required coordination: [runGuidanceController](../../extension/src/content/runGuidanceController.js), [scopedPersistenceTransaction](../../extension/src/shared/scopedPersistenceTransaction.js), [nativeRequestIdentity](../../extension/src/shared/nativeRequestIdentity.js). - Verification: [writebackCancellationFlow](../../test/writebackCancellationFlow.test.js) checks cancellation before and during mutations; [activeTurnControl](../../test/activeTurnControl.test.js) checks orphan and live-run recovery decisions. Queue/Steer UI changes need a focused submit-and-refresh check.
- Submission waits for the official skills catalog when required. Guide uses task-only preflight and revalidates identity after compatibility waits. - Immediate Steer bubbles and historical placement: `RunGuidanceController` owns the in-flight memory projection; `getPendingGuidance → RunTimelineView/RunActivitySummary → RunGuidanceView.reconcileGuidance` keeps follow-up input between the original input and runtime. ## Snapshots, Mirrors, Writeback, and Undo

Display diffs and executable patches are generated by Native [diffEngine.computeLineDiff](../../native-host/src/diffEngine.js) and [textPatch.computeTextPatches](../../native-host/src/textPatch.js) respectively; [StaleGuard.prepareOperationPatches](../../extension/src/shared/staleGuard.js) converts newline coordinates between the source and editor, and Page `applyTextPatches` checks and applies them. ### Change the compatible Bootstrap migration from 2.5.0 to 2.5.1

- The entry point remains `Update now`; the old updater installs the new runtime first, then [backgroundBootstrapMigration](../../extension/src/backgroundBootstrapMigration.js) continues through `update.status → update.bootstrap → chrome.runtime.reload → update.confirm`. The new Bootstrap revision is `3.1`, while the installation protocol remains `3`; Chrome permissions are not expanded and the user-level bridge is not rewritten.
- [bootstrapMigrationContract](../../native-host/src/bootstrapMigrationContract.js) constrains the version pair, actual source digest, and closed file list; [runtimeInstaller](../../native-host/src/runtimeInstaller.js) places the payload within the Native subtree allowed by the old archiver, [build-release](../../scripts/build-release.mjs) generates the description covered by the signature, and artifact verification checks bytes in each package.
- State owners: [bootstrapUpdate](../../native-host/src/bootstrapUpdate.js) binds the original signature, consent, and main transaction; [bootstrapMigration](../../native-host/src/bootstrapMigration.js) stores independent file backups/progress and performs atomic replacement; [bootstrapUpdateWatchdog](../../native-host/src/bootstrapUpdateWatchdog.js) supervises outside the browser worker. `updateManager` restores and verifies the fixed layer, runtime, and metadata before switching back to the source Native pointer.
- Recovery finalization: rollback before the first status call also binds to a known migration; while pending with no file WAL yet, observed source-byte evidence is stored in `rollbackEvidence.bootstrapSha256`, and `sourceUnchanged` marks the untouched-file path. `sourceActivationPending` keeps the watchdog completing consent and pointer restoration for a recovered terminal state, with the persisted runtime and Bootstrap digests rechecked before switching the pointer; `committedEvidence` makes cleanup on a restart after commit recheck the runtime, Bootstrap digest, and exact consent ownership.
- For transaction persistence, inspect `updateManager.atomicWriteText`: a temporary file is written and fsynced through the same writable handle before rename; the Windows directory-flush exception does not apply to ordinary files. See [installation migration details](installation-and-updates.md#5-normal-flow-from-discovery-to-confirmation) for platform and persistence boundaries.
- Required coordination: `bootstrap_pending` prevents premature confirmation by the old worker; also check background and Native business-operation barriers, loaded revisions and disk digests, target syntax/permission-shape validation, Native recovery wake-up when the original Popup fails to load, strict transaction ownership, and reload counts. The original fixed Native launcher still checks only whether the entry point exists; automatic recovery cannot be assumed when the target Native itself cannot start.
- When the original content receiver is unreachable after the first extension reload, inspect transaction/document binding and targeted injection in [backgroundUpdateSafety](../../extension/src/backgroundUpdateSafety.js), the isolated-world read-only receiver in [updateSafetyReceiver](../../extension/src/content/updateSafetyReceiver.js), and MAIN-world save observation in [updateSafetyProbe](../../extension/src/page/updateSafetyProbe.js). These reuse `UpdateIdle/saveState`, retain waits for inactivity and stable saving, and do not reconstruct the full panel or business runtime.
- The page-reload list is managed by `protectReloadTabs/releaseReloadTabs` and `codex-overleaf-managed-update-guarded-tabs-v1`: only after a safe point is established before continuing target health verification or after source rollback is the list for the same documents returned to the old Bootstrap entry point. Verify disk rollback, page saving, and permission to refresh separately; loss of the worker must not let the old list automatically refresh unsaved pages. See [installation safe points](installation-and-updates.md#6-actual-scope-of-safe-points) for the full boundary.
- When changing update safety, verify the affected receiver/probe and saved-page decision. After the Native gate, tabs must be enumerated again and recovered documents probed again. Retiring an old guard requires the captured document to be gone; comparing only tab IDs or version numbers is insufficient.
- Validate the supported upgrade using `verify:update-boundary` and an update-hop from a real older version. The latter starts the actual new Native through [update-hop-runtime](../../scripts/update-hop-runtime.mjs), then executes installed fixed scripts through [update-hop-bootstrap-harness](../../scripts/update-hop-bootstrap-harness.mjs); the harness supplies Chrome APIs/page health. File fault injection, VM execution, actual Native processes and real Chrome provide separate evidence; see [Installation and updates](installation-and-updates.md).

## Loading Checklist for New Modules and Capabilities

Content source modules follow this sequence; source entry points and browser injection lists have different responsibilities.

1. Add the canonical source import to [content-entry.mjs](../../extension/entries/content-entry.mjs); declare explicit dependencies through [ModuleRegistry.define](../../extension/src/content/moduleRegistryKernel.js).
2. When direct exposure to the composition root is needed, update the dependency set in [legacyGlobalRegistry](../../extension/src/content/legacyGlobalRegistry.js); assemble callbacks/getters in [contentRuntime](../../extension/src/content/contentRuntime.js).
3. Generate the bundle and metadata through [build-content-bundle](../../scripts/build-content-bundle.mjs); do not edit generated files manually. This operation writes build artifacts.
4. The [direct manifest](../../extension/manifest.json) and [runtime manifest](../../extension/runtime-manifest.json) currently list one content bundle each; adding an ordinary content module does not append source scripts to either manifest.
5. Build the actual entry using [build-content-bundle](../../scripts/build-content-bundle.mjs), then verify mounting in Chrome. The [module graph command](../../scripts/check-content-module-graph.mjs) is a build alias; it no longer imposes source-layout or size budgets.

Currently, `SensitivePreflight` is exposed to runtime through the content-entry import and legacyGlobalRegistry, with runtime injecting construction dependencies; this only relocates Content preflight responsibilities and adds no Page resources. Native `nativeRunLifecycle` enters taskRunnerRuntime through CommonJS require, then exports the shutdown API to index, independently of the browser bundle. New helpers must connect through their own execution environments and be checked against actual consumers.

Page-world capabilities follow a separate checklist: implementation → RPC contract → resource exposure → ordered injection → dispatcher → verification.

1. Implement the capability in a page module, classify read/write operations, identity requirements, and timeouts in [pageRpcContract](../../extension/src/shared/pageRpcContract.js), and wire the dispatcher/capability in [pageBridge](../../extension/src/pageBridge.js).
2. Check that [direct WAR](../../extension/manifest.json) and [managed WAR](../../extension/bootstrap/manifest.template.json) cover the required resources; managed already uses shared/page wildcard lists.
3. Update [pageBridgeClient.PAGE_WORLD_SCRIPTS / injectPageBridge](../../extension/src/content/pageBridgeClient.js) while preserving dependency order; runtime only creates and starts the client.
4. Invoke the changed method through the actual Page dispatcher. For mutations, check missing/incorrect project identity and duplicate delivery; [documentIntegrity](../../test/documentIntegrity.test.js) and [writebackReceiptRecovery](../../test/writebackReceiptRecovery.test.js) provide representative contracts, not an exhaustive method inventory.

Changes along any route must first capture and bind the owning project, session, and run identities, then examine asynchronous results and persistence; a UI display of “completed” should be traceable to the corresponding execution, write, save, or undo evidence.
