# Feature Change Navigation

Initial reference product version: `2.5.0`; initial reference source baseline: `2073ae7`. This index is maintained alongside the current repository; task execution and synchronization requirements are defined in the [development and repair SOP](change-workflow.md).
This page records entry points, state owners, required coordinated changes, and verification routes for the current implementation. An owner is the module with authority over a state or behavioral decision; the UI usually displays a projection of that state.

Start here: [Architecture guide home](README.md) · [System overview](system-overview.md).
Core flows: [Auto editing and Undo](auto-edit-undo.md), [Run state and recovery](run-state-and-recovery.md). Other domain pages expand the main paths and failure boundaries in the groups below; implementation changes still require checking the corresponding source.
Navigation method: first match the user's intended change, then follow “entry point → state owner → coordinated changes → verification”; symbol names can be used directly in source searches.
Verification entries below apply to the path being changed. They distinguish retained automated contracts from focused manual checks; they do not form a mandatory full release matrix.

## UI, Settings, and Diagnostics

Domain guide: [UI and loading](ui-and-loading.md).

### Change the panel entry point, width, or layout

- Entry points: [PanelRenderer.create](../../extension/src/content/panelRenderer.js); [ContentRuntime.ensurePanelOpen](../../extension/src/content/contentRuntime.js) assembles the slots.
- State owner: PanelRenderer manages the DOM and resizing; width enters runtime/prefs, while launcher visibility is stored separately in `chrome.storage.local['codex-overleaf:launcher-visible']`. Whether the panel is open is DOM state; initialization after a refresh reopens the panel.
- Required coordination: [panel.css](../../extension/styles/panel.css), [sessionState](../../extension/src/shared/sessionState.js); preserve the settings, session, and composer lifecycles.
- Header: the active session title is the switcher trigger ([SessionMenuView](../../extension/src/content/sessionMenuView.js)) with per-row deletion through `renderSessionMenu → deleteSessionWithConfirm`, and the diagnostics trigger carries a health label and the Refresh file status menu action; the Sessions list slot is hidden. See [header session switcher](ui-and-loading.md#header-session-switcher).
- Text sizes and colours: use the `--tl-text-*` scale and `--tl-*` colour tokens in [panel.css](../../extension/styles/panel.css); see [type scale and colour tokens](ui-and-loading.md#panel-type-scale).
- Verification: When changing this surface, open/close and resize the actual panel; verify its affected layout after refresh, in both themes.

### Change runtime activity, reading follow behavior, the latest button, or answer copying

- Entry points: [RunTimelineView.bindLogAutoFollow/scrollLogToBottom](../../extension/src/content/runTimelineView.js), `configureCopyButton` in [RunResultActions](../../extension/src/content/runResultActions.js).
- State owner: the timeline manages follow intent, unread steps, and forced jumps; [RunScrollLayout](../../extension/src/content/runScrollLayout.js) preserves the reading anchor before repaint. Copying extracts the current answer DOM on click, preserving block structure and copying math as TeX source, excluding the run log and raw Markdown.
- Required coordination: streaming output, collapsing, repainting, font and width changes, the Clipboard API/fallback, and action failure notices. See [UI and loading](ui-and-loading.md) for details.
- Collapsed activity: [RunActivityModel.project](../../extension/src/shared/runActivityModel.js) combines saved events with incoming display snapshots by stream identity; [RunActivitySummary.renderPeek](../../extension/src/content/runActivitySummary.js) owns the three-row window. Coordinate runtime `appendRunEvent`/`upsertRunStreamRecordEvent`, session normalization, and the timeline's stream and elapsed-timer refreshes; see [activity projection](ui-and-loading.md#activity-projection-and-post-write-receipts).
- Verification: When changing this path, use a long answer to check manual scrolling, the latest button, and copied conclusion text.
- For activity-only changes, check that repeated updates of one Thinking stream preserve the three rows and their node identity, while a new stream can advance the window. Include current-record updates after session normalization, completion and history reconstruction; source-string and CSS assertions do not establish these behaviors.

### Change compile-log references or the compile-error repair entry point

- Entry points: runtime `renderAtFileMenu/runTask` parses `@compile-log`, while `appendCompileFix` in [RunTimelineView](../../extension/src/content/runTimelineView.js) refills the draft.
- State owners: [CompileBridge](../../extension/src/page/compileBridge.js) manages `recentCompileCaptures`, bounded by `MAX_RECENT_COMPILE_CAPTURES`, and monotonically advancing source-edit stamps; [WritebackOrchestrator.resolveCompileLogContext](../../extension/src/content/writebackOrchestrator.js) coordinates log retrieval.
- Compile controls: `CompileBridge.findOverleafCompileButton` prefers Overleaf's main `.compile-button`, with an exact normalized English/Chinese Recompile or Compile label as fallback. It excludes Codex UI roots, dropdown toggles, menu items and Stop compile. A disabled or Compiling main button remains the selected control; the bridge never searches for another enabled compile-related control. `inFlightCompileRequests` also blocks new clicks and template POSTs while an observed request is pending. An eligible completed capture is reused; if the in-flight request predates the write or otherwise supplies no eligible capture, the bridge clicks the main button at most once after it becomes idle. The same capture timeout bounds the wait; no qualifying result remains triggered.
- Post-write evidence: `WritebackOrchestrator.autoRecompileAfterWriteback` uses that trigger path, then passes the captured `captureId` to `getCompileLog`. `CompileBridge` observes `window.fetch` POST requests to `/project/:id/compile`, recording the source stamp at request time and completion time. A completed capture covering the source stamp at trigger time can satisfy the wait, including a request already in flight after the write; a request preceding the write cannot. Older responses cannot replace the newest capture. Reading a named capture does not require it to remain the latest request: a later compile of unchanged source is allowed, while a later source edit or excessive completion age invalidates freshness before or after the log read. `FETCH_WRAPPER_REVISION` controls wrapper replacement on reinjection: retain another script's wrapping chain and isolate legacy capture state; coordinate the shared `pageRpcContract.REVISION` bump.
- Log routing: `CompileAdapter.parseCompileResponse` prefers `output.log` and retains its `build`, an absolute HTTPS `pdfDownloadDomain`, and a validated `clsiServerId` token. `getCompileLog` first tries `pdfDownloadDomain + logUrl` when build/domain metadata exists; this assumes Overleaf's `pdfDownloadDomain` already includes any `outputUrlPrefix`, which the bridge does not add. The origin fallback appends `clsiserverid` when available. HTTP/network failure tries the other candidate. Fetches use `cache: 'no-store'` and omit cross-origin credentials. The bridge does not consume Overleaf's parsed UI log entries or infer success from a PDF.
- Result contract: [CompileAdapter.buildPostWriteCompileSummary](../../extension/src/shared/compileAdapter.js) requires a captured successful response not marked `fromCache` and a matching fresh log result with `ok:true` and no parsed errors before reporting success; [CompileBridge.getCompileLog](../../extension/src/page/compileBridge.js) sets `ok` only for a nonempty log. `parseLogErrors` recognizes TeX `!`, file-and-line diagnostics, and runaway arguments, and counts only the `LaTeX`, `LaTeX3` and `LaTeX Font` warnings and the Package/Class/Module warning forms, the forms Overleaf's log parser is understood to report (agreement with the deployed parser is not verified here); the existing parser bound remains 50 errors, while the conclusion displays the first three. Diagnostic context stops at whitespace-only lines, preserving the `l.N` line and excluding later PDF-output notices. An explicit compiler failure without readable diagnostics retains one generic error unless freshness evidence invalidates that capture. Uncaptured triggers remain triggered; missing, stale, mismatched, empty, cached-success, or otherwise unknown result evidence is unconfirmed. The existing compile activity output retains technical reasons such as HTTP/network failure, stale source, expiry or missing capture. Failed compile evidence supplies the existing `compileErrors` repair draft without changing write/save/settlement facts. Historical reports are not rewritten. `StorageDb.compactRunEventsForStorage` preserves bounded `compileErrors` and `rejectedHunks` for repair actions after hydration; it does not reconstruct payloads already absent from old records.
- Required coordination: the refresh and identity policies of `getCompileLog`, [RunController](../../extension/src/content/runController.js) arguments, [codexPromptAssembly](../../native-host/src/codexPromptAssembly.js), and continuation after failure. Explicit log requests and automatic compilation after writing use two separate entry points; see [UI and loading](ui-and-loading.md).

2. When direct exposure to the composition root is needed, update the dependency set in [legacyGlobalRegistry](../../extension/src/content/legacyGlobalRegistry.js); assemble callbacks/getters in [contentRuntime](../../extension/src/content/contentRuntime.js).
3. Generate the bundle and metadata through [build-content-bundle](../../scripts/build-content-bundle.mjs); do not edit generated files manually. This operation writes build artifacts.
4. The [direct manifest](../../extension/manifest.json) and [runtime manifest](../../extension/runtime-manifest.json) currently list one content bundle each; adding an ordinary content module does not append source scripts to either manifest.
5. Build the actual entry using [build-content-bundle](../../scripts/build-content-bundle.mjs), then verify mounting in Chrome. The [module graph command](../../scripts/check-content-module-graph.mjs) is a build alias; it no longer imposes source-layout or size budgets.

Currently, `SensitivePreflight` is exposed to runtime through the content-entry import and legacyGlobalRegistry, with runtime injecting construction dependencies; this only relocates Content preflight responsibilities and adds no Page resources. Native `nativeRunLifecycle` enters taskRunnerRuntime through CommonJS require, then exports the shutdown API to index, independently of the browser bundle. New helpers must connect through their own execution environments and be checked against actual consumers.

Page-world capabilities follow a separate checklist: implementation → RPC contract → resource exposure → ordered injection → dispatcher → verification.

1. Implement the capability in a page module, classify read/write operations, identity requirements, and timeouts in [pageRpcContract](../../extension/src/shared/pageRpcContract.js), and wire the dispatcher/capability in [pageBridge](../../extension/src/pageBridge.js).
2. Check that [direct WAR](../../extension/manifest.json) and [managed WAR](../../extension/bootstrap/manifest.template.json) cover the required resources; managed already uses shared/page wildcard lists.
3. Update [pageBridgeClient.PAGE_WORLD_SCRIPTS / injectPageBridge](../../extension/src/content/pageBridgeClient.js) while preserving dependency order; runtime only creates and starts the client.
4. Invoke the changed method through the actual Page dispatcher. For mutations, check missing/incorrect project identity and duplicate delivery; [documentIntegrity](../../test/documentIntegrity.test.js) and [writebackReceiptRecovery](../../test/writebackReceiptRecovery.test.js) provide representative contracts, not an exhaustive method inventory.

Changes along any route must first capture and bind the owning project, session, and run identities, then examine asynchronous results and persistence; a UI display of “completed” should be traceable to the corresponding execution, write, save, or undo evidence.
