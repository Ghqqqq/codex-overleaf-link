# UI, Loading, and Input Context

Initial source reference baseline: `2073ae74747431aab8d529803d4e9f8197262388`. Current behavior is maintained alongside this repository's implementation.
This page covers the UI domain in the [system overview](system-overview.md) and [feature map](feature-map.md). For complete run ownership, see [run state and recovery](run-state-and-recovery.md); for write evidence, see [Auto editing and Undo](auto-edit-undo.md).
Source behavior, retained test coverage, and browser interaction acceptance are described separately. The change-driven checks below apply to the affected path; they are not an expanded release checklist.

## 1. Two Execution Worlds and Two Installation Entry Points

The isolated world is the extension's isolated JavaScript environment, responsible for the panel, state coordination, and messaging. The MAIN world is the Overleaf page environment, responsible for accessing the editor and page capabilities.
They share the page DOM but have separate JavaScript global environments. WAR (web-accessible resources) allows the page to load specified extension resources; it does not execute scripts itself.

```text
content-entry.mjs                         ← canonical source inclusion
  ├─ moduleRegistryKernel / shared / content / vendor
  ├─ legacyGlobalRegistry.create(globalThis)
  └─ ContentRuntime.init(dependencies)
          ↑ built into generated/content.bundle.js
          ├─ Direct: manifest.content_scripts
          └─ Managed: bootstrap.registerManagedRuntime
                      → runtimeContext.js + runtime/<bundle>
ContentRuntime
  └─ PageBridgeClient.start / call
      → PAGE_WORLD_SCRIPTS / OPTIONAL_OT_SCRIPTS
      → MAIN world pageBridge.dispatch
```

The source inclusion entry point is [content-entry.mjs](../../extension/entries/content-entry.mjs). [buildContentBundle](../../scripts/build-content-bundle.mjs) reads classic modules through this entry point, builds an IIFE in isolated wrappers, and generates the bundle and metadata/source digest.
Changing an import in the entry point therefore changes the output; editing the generated bundle directly will be overwritten by a later build. This digest covers content build inputs and cannot alone prove that Native, MAIN world, and the copy loaded by the current browser are aligned.

| Injection surface | Current entry point | Checks when changing it |
| --- | --- | --- |
| Direct unpacked | `content_scripts` in [manifest.json](../../extension/manifest.json) | Currently lists only one content bundle; the CSS list is maintained separately |
| Managed runtime | `registerManagedRuntime` in [bootstrap/background.js](../../extension/bootstrap/background.js) reads [runtime-manifest.json](../../extension/runtime-manifest.json) | Validates the manifest before dynamic registration and filters matches by authorized sites |
| Managed path adaptation | [runtimeContext.js](../../extension/bootstrap/runtimeContext.js) | Sets `__CODEX_OVERLEAF_RUNTIME_PREFIX__ = 'runtime/'`; page resource URLs receive this prefix |
| Page resources | Direct WAR and the [bootstrap manifest](../../extension/bootstrap/manifest.template.json) | Direct explicit entries and Managed coverage such as `runtime/src/shared/*` and `runtime/src/page/*` |

Managed migration must distinguish extension reload from page refresh: the old panel DOM may remain while the old isolated-world message receiver has become invalid. When the migration transaction is locked and the old probe is unreachable, [backgroundUpdateSafety](../../extension/src/backgroundUpdateSafety.js) currently injects [updateSafetyReceiver](../../extension/src/content/updateSafetyReceiver.js) and [updateSafetyProbe](../../extension/src/page/updateSafetyProbe.js) into the specific Chrome document ID. This path restores only safety probing and reuses the save/quiescence rules; it does not rebuild the complete content runtime, Page Bridge, or panel. The presence of panel DOM and a single-panel check cannot replace receiver/version health evidence.

The migration controller protects the original page auto-refresh list: while waiting, it moves the list into guarded storage. It restores the list using the original document identities after the target fixed layer confirms loading, or after the source version has been restored and the page reaches a safe point again. A page may still have unsaved content when disk rollback finishes, so refresh eligibility must be determined independently. For the owners and failure boundaries, see [installation safe points](installation-and-updates.md#6-actual-scope-of-safe-points).

### Registry and Composition Root

[ModuleRegistry.define/resolve](../../extension/src/content/moduleRegistryKernel.js) stores named definitions, resolves explicit dependencies, and caches instances. Missing dependencies, dependency cycles, or missing valid exports produce controlled errors.
The current migration still supports legacy `CodexOverleaf*` global publication. `define` defers resolution through getters; [LegacyGlobalRegistry.create](../../extension/src/content/legacyGlobalRegistry.js) reads `REQUIRED_MODULES/SUPPORT_MODULES` and constructs the runtime's `modules`.
Missing exports in `SUPPORT_MODULES` also enter the error set; the word support in the name does not make them freely optional.
Shared modules must still follow initialization order: [content-entry](../../extension/entries/content-entry.mjs) loads `StaleGuard` before `UndoOperations`, which uses its patch-coordinate mapping; `WritebackSettlement` declares `UndoOperations` as an explicit registry dependency. Changes to recovery material require checking both CommonJS and browser assembly paths.
[ContentRuntime.init](../../extension/src/content/contentRuntime.js) is the composition entry point, injecting getters/callbacks into each controller. This file still contains business workflows, so its entire contents cannot be classified as pure composition.
[RunReviewController](../../extension/src/content/runReviewController.js) owns Undo/Accept orchestration; [DirectoryCleanupRecovery](../../extension/src/content/directoryCleanupRecovery.js) stores directory observations. The runtime orchestrates existing creation retries and save confirmation, checking account, project, run, and persistence dependencies. [RunCompletionMeta](../../extension/src/content/runCompletionMeta.js) and [RunRecoveryActions](../../extension/src/content/runRecoveryActions.js) respectively own result metadata and existing recovery actions.
The runtime marks initialization to prevent duplicates. If an old panel already exists in the DOM before runtime registration, it returns `stale-panel-before-runtime-init`. This guard does not prove that every old page has recovered automatically.
Asynchronous initialization loads global preferences, account scope, and persistent state before creating the queue, panel, and recovery flows. The project-list route mounts the dashboard shell immediately and fills its list later.
Queue data loading and queue-card rendering have separate entry points, connected by panel synchronization. For the display path after initialization and recovery, see [queue display and recovery entry points](#pending-queue-render).

### Independent MAIN-World Assembly

[PageBridgeClient](../../extension/src/content/pageBridgeClient.js) owns ordering through `PAGE_WORLD_SCRIPTS`, `OPTIONAL_OT_SCRIPTS`, and `injectPageBridge`; the runtime only creates and starts the client.
`injectPageBridge` attempts optional OT dependencies before capability modules. Failure in this optional portion allows an unavailable fallback; failure to load other required scripts makes `call` return bridge unavailable.
`injectScriptOnce` builds the resource URL and waits for load/error/timeout; the list entry's third member, `force`, affects handling of existing script nodes. Script assembly must still be followed by the `initializeCapability` handshake.
Method policies come from [pageRpcContract.METHODS](../../extension/src/shared/pageRpcContract.js), while actual dispatch occurs in [pageBridge.dispatch](../../extension/src/pageBridge.js). New methods must also define identity, timeout, cancellation, and replay semantics.
`pageBridge` uses both the product version and `pageRpcContract.REVISION` to determine whether it is already installed; when both match, it retains the old instance. If a Page implementation change requires rebuilding closures such as the router, update the shared revision too, so reinjection of the same version loads the new behavior. Client response validation uses the same constant. This does not replace acceptance testing of actual extension reload and page refresh.
Read identity policy separately for each method. Project identity remains optional for `ensureReviewing/ensureEditing`; `dispatch()` applies the corresponding guard only when identity is supplied. When changing page mode, check whether callers pass the captured project identity; see [Auto editing and Undo](auto-edit-undo.md).

## 2. Panel and Settings: DOM as a Projection of State

Projection means displaying existing state as controls, labels, and cards. A button's checked state resembles an instrument needle: the persistent owner determines its reading. Rebuilding DOM should reproject that state without rewriting run history.

| Surface | Creation/layout owner | Behavior and data source |
| --- | --- | --- |
| Panel shell, launcher, draggable width | [PanelRenderer.create](../../extension/src/content/panelRenderer.js) | Runtime `ensurePanelOpen` supplies action callbacks; the renderer manages listeners and width |
| Header session switcher | `[data-session-label]` markup in [PanelRenderer.create](../../extension/src/content/panelRenderer.js); behavior in [SessionMenuView](../../extension/src/content/sessionMenuView.js) | The active session title is the menu trigger; each listed session has Switch and Delete controls, followed by the New / Rename / Delete footer. The `CODEX` label is shown only on the recent-projects dashboard |
| `diagnosticsSlot` | [DiagnosticsPanel](../../extension/src/content/diagnosticsPanel.js) | DiagnosticsController performs checks; result display does not own the underlying environment state. The header trigger shows the health dot plus a short state label; its menu starts with Refresh file status, wired to runtime `refreshProbe` |
| `settingsSlot` | [SettingsPanel.create](../../extension/src/content/settingsPanel.js) | Settings coordinators, global preferences, and the corresponding domain owners |
| `sessionSlot` | [SessionPanel](../../extension/src/content/sessionPanel.js) | Still created and updated by the runtime, but hidden by CSS; the header switcher is the visible session control |
| `composerSlot` | [ComposerPanel.create](../../extension/src/content/composerPanel.js) | Runtime callbacks for submission, cancellation, models, context, and attachments |
| Timeline scrolling and the latest button | [RunTimelineView](../../extension/src/content/runTimelineView.js), [RunScrollLayout](../../extension/src/content/runScrollLayout.js) | The former manages follow intent and unread steps; the latter restores reading position after layout changes and redraws |
| Project-list dashboard | [RecentProjects](../../extension/src/content/recentProjects.js) | Account-scoped session summaries and the SPA route; it should not first flash the project composer |

`PanelRenderer.setLauncherVisible/initializeLauncherVisibility` independently reads and writes the side launcher's enabled preference in extension `chrome.storage.local['codex-overleaf:launcher-visible']` and listens for storage changes. This does not go through session persistence or GlobalPreferencesController.
`isLauncherVisible` returns whether the launcher is enabled; actual visibility additionally requires the panel to be closed. Clicking the launcher opens the panel through runtime `ensurePanelOpen`; the close button calls `setVisible` through `closePanel`. Open/closed state is stored in the DOM's `is-open` class.
Runtime `init` calls `ensurePanelOpen` after loading state, so a page refresh reopens the panel. Disabling the launcher preference affects only the button shown when the panel is closed. When changing this path, check launcher enablement, panel closing/opening, and a page refresh in Chrome.

<a id="header-session-switcher"></a>

**Header session switcher and health label.** `PanelRenderer.create` renders `[data-session-label]` (title text, chevron, rename input and `[data-session-menu]`) inside the header. [SessionMenuView](../../extension/src/content/sessionMenuView.js), created by `SessionManager` with `PanelIcons` from the composition root, owns the behavior: `applySessionLabel` writes the active title and a tooltip combining it with the switch action; `toggleSessionMenu/renderSessionMenu` list displayable sessions newest first and append a footer with New, Rename (`beginActiveSessionRename`, inline in the header) and Delete (`deleteSessionWithConfirm`, disabled for a running or sole empty session). `renderSessionMenu` uses a `.codex-session-menu-item` container with sibling switch and delete buttons, avoiding nested buttons. Hover or focus within the row reveals its delete control and hides the time; the control uses `PanelIcons.svg('close')`, closes the menu before calling `deleteSessionWithConfirm(session.id)`, and is disabled for running sessions with the localized `deleteRunningSession` tooltip. Confirmation, empty-session rules and persistence remain owned by SessionManager. Outside clicks and Escape close the menu. Session lifecycle rules are unchanged; see [session lifecycle](run-state-and-recovery.md#session-lifecycle). The `[data-session-slot]` list stays mounted for its existing update calls but is hidden, and on `data-view="recent-projects"` the switcher is hidden and the plain `CODEX` label returns. Refresh is the first action in the health menu, rather than a separate header button; see [diagnostics entry points](#7-actual-entry-points-for-diagnostics-and-popup). `DiagnosticsPanel.updateStatus` also writes `[data-diagnostics-health-label]` (`diagnosticsPill*` keys: Ready / Attention / Problem / Checking) and `data-health` on the trigger; the label summarizes the same health bucket as the dot and its existing tooltip, so it adds no new health source. When changing the header, check a long title at the 380px default width, the open menu in both themes, rename/delete through the menu, and the dashboard view.

`RunTimelineView.bindLogAutoFollow` captures reading intent from wheel, touch, pointer, and keyboard events. `logAutoFollow` determines whether new output continues scrolling to the bottom; `scrollLogToBottom` coalesces requests within a frame and rechecks intent when drawing.
`ensureJumpToLatestButton` creates the latest button. Clicking it calls `scrollLogToBottom({ force: true })`, reenables following, and clears unread steps. `.tl-jump-latest` uses an opaque `--tl-surface-1` background, a `--tl-border-strong` border and a `--tl-surface-0` halo to separate it from underlying text in both themes. This count tracks discrete steps after leaving the bottom; streaming increments on an existing row do not add one count per chunk.
A reading anchor works like a bookmark: [RunScrollLayout.captureAnchor/snapshot/restore](../../extension/src/content/runScrollLayout.js) stores a visible paragraph's offset relative to its container and rebinds the node by run ID and paragraph index after a redraw. If no corresponding node exists, it falls back to the saved scroll offset. `renderRunHistory` uses this recovery path only with `preserveScroll:true` after following has been disabled; other redraws force scrolling to the bottom by default.
When changing scrolling, use a long answer in Chrome to check leaving the bottom, returning with the latest button, and preserving a visible paragraph through the affected redraw.

[SettingsWorkbench.mount](../../extension/src/content/settingsWorkbench.js) moves existing settings-group DOM into a native `<dialog>`. `SECTIONS` splits the sidebar by scope: "This project" holds Writing, Protection & privacy, Project cache and History; "All projects" holds Appearance, Models & connections, Context & skills, Local data and Software updates. `GROUP_PAGES` places each `data-set-group` on a page, and a page's section decides whether its groups need an open project (`hasProject`, false on the dashboard where `data-settings-scope="account"`); unmapped groups and leftover nodes fall back through `FALLBACK_PAGES` by their original scope. Without a project the whole "This project" section and its pages are hidden. The section headings are visual (`aria-hidden`); each tab references its heading through `aria-describedby`, and arrow/Home/End keys move across both sections. Each page states its scope once in `.codex-wb-page-scope` under the title ("Only for this project · <project name>" or "Applies to all projects"); the name comes from the `getProjectName` option that the runtime passes to `SettingsPanel.create` (`recentProjects.readCurrentProjectNameFromDom`) and may be empty. The dialog title sits at the top of the rail and the close button floats over the content's top-right corner.
Groups are plain sections: the summary is not focusable, its click is cancelled, no chevron, scope chip or hover band is drawn, and `refresh` sets a group open exactly while its page is shown, which keeps the history and storage `toggle` loaders lazy. Rows hang from one hairline under the section title and are separated by hairlines; a help paragraph after a switch or select row attaches to that row; every secondary action, including the history retry and "more" buttons and the Provider page's Add/Refresh, uses one bordered button style, and danger actions only tint text and border. Glob-rule textareas use a monospace face. After visibility and locale refresh, `refreshSoleSections` sets `data-sole-section="true"` when the only visible group repeats the page title; the group title is then hidden while its Saved mark stays visible above the first hairline. Pages are capped at 600px wide; the body padding and the footer status share one side gutter. The Skills subpage keeps the dialog size and the sidebar, with Context & skills selected (`SKILLS_PAGE`).
**Footer status.** `SettingsPanel.setStatus(target, text, status, { page })` writes the shared `[data-project-settings-status]` footer. A `page` option records `data-status-page`; `refresh` in the workbench hides a tagged message while another category is active, and `clearStatus` removes the tag. Untagged messages show on every page. Skill catalog, selection and removal messages from [ProjectSettingsCoordinator](../../extension/src/content/projectSettingsCoordinator.js) (`SKILLS_STATUS`) and LocalSkillsPanel are tagged `context`, the page holding the Skills group, so a failed skill listing does not appear on unrelated pages. A failed status renders as a tinted banner; its text keeps the language in effect when it was written.
Moving nodes retains existing listeners and drafts; new controls should still define their read/write interfaces in SettingsPanel. Adding a navigation button does not automatically create a persistent field.
Page placement only decides where a field is shown. Moving a group to another section does not migrate the field's storage scope.
`show` uses `showModal()` and saves the prior focus; `hide` attempts to restore focus after closing. `requestClose` first runs the Provider close guard, then notifies the original close callback.
The dialog's `cancel` handler only processes events targeting the dialog, preventing file-picker cancellation from accidentally closing settings. Category switching and closing must preserve this lifecycle constraint.
Providers enter the workbench through `revealProviders`; [ProviderSettingsDialog](../../extension/src/content/providerSettingsDialog.js) and [ProviderSettingsCoordinator](../../extension/src/content/providerSettingsCoordinator.js) manage their editors. In the embedded Provider page, `.codex-provider-dialog-foot` is sticky only while `.codex-provider-footer-actions` holds buttons; a footer carrying only the operation status flows after the content, so it never covers the detail card. Failed operation status uses the same tinted banner as the settings footer, and the Built-in detail card spans the page width. Embedded provider buttons sit under the panel-wide `#codex-overleaf-panel button` reset, so the embedded rules restate their border; danger buttons keep red text and border, and in the provider confirmation dialog the destructive answer is a filled danger button beside a bordered cancel.
Ordinary theme options still use the existing select as the value entry point; Workbench theme cards trigger its input/change events. New visual proxy controls should continue using existing state paths.
Visible native selects (`select.codex-set-select` in settings and every select in the Provider dialog) use `appearance: base-select` under `@supports`, so their option list, checkmark and chevron follow the surrounding surface through the `--codex-select-*` tokens mapped from panel, workbench or Provider tokens. They remain native selects: value, `change`/`input` events, keyboard selection and accessibility are unchanged, and browsers without customizable selects keep the system popup. Selects with their own chevron hide `::picker-icon`.

[LocalSkillsPanel](../../extension/src/content/localSkillsPanel.js) renders local Codex and Codex Overleaf catalogs separately on the Skills page. Both lists use the existing row layout and per-item switches; local items offer no delete action. `refreshLocalSkills` reads the local catalog through runtime `primeCodexLocalSkillsCatalog`. Loading, empty catalogs, and failure have separate English/Chinese states; reopening the page can refresh the catalog. Failure to discover an individual item retains the valid catalog and displays a partial-loading warning using `discoveryWarnings` codes and counts, without blocking ordinary tasks. The catalog is held only in memory; the global owner persists preferences.
`contentRuntime.getSlashCommands` adds enabled local items to the `/` menu, retaining the `codex-local` scope and stable IDs. Selection submits through existing composer skill chips. Plugin skills with identical names retain separate identities. For catalog discovery, selection defaults, and explicit Native reads, see [catalog, per-item selection, and invocation](writing-style-and-skills.md#local-skill-catalog). UI changes must also check submission capture, the queue, and actual execution isolation. When changing this path, verify the visible catalog, selected skill chip and one actual invocation.

`/` and `@` share `.codex-slash-menu`. Internal vertical scrolling accommodates long lists without truncating available skills. [panel.css](../../extension/styles/panel.css) provides the height limit, scroll boundaries, and long-text wrapping; `contentRuntime.updateSlashMenuLayout` calculates available space from the composer's top edge and the panel/visible viewport's top edge. [ComposerPanel](../../extension/src/content/composerPanel.js) listens for window and visualViewport changes and uses ResizeObserver for composer, mount-container, and panel dimensions; destruction removes these subscriptions. Rerendering or filtering resets both selection and scroll position to the first item/top. Arrow keys use `setSlashMenuActiveIndex` to change only the menu's scrollTop and reveal the selected item, without scrolling conversation content or the editor. Layout changes retain the current scroll position; the next keyboard selection realigns the highlighted item. IME, Enter, Escape, and existing `@` selection semantics remain unchanged. When changing menu geometry, check wheel/trackpad scrolling, keyboard selection, and a narrow panel with a long catalog.

`renderSlashMenu` groups `/` entries by their `group` (commands, Codex Overleaf skills, local Codex skills) under non-selectable labels; `@` entries carry no group. Each row shows a [PanelIcons](../../extension/src/shared/panelIcons.js) tile for its kind, highlights the typed query in the title and the `/compact` tag, and clamps the subtitle to two lines with the full text as a tooltip. Local skills use their catalog `preview` after any plugin source or duplicate-name hint. `/compact` shows the current reported usage with the same high/near-limit levels as the context indicator. A sticky key-hint row ends the menu; its `kbd` key caps set background, border, shadow and color explicitly because Overleaf's Bootstrap styles every `kbd` with a dark fill; `setSlashMenuActiveIndex` subtracts its height when revealing the selection and returns to the top when selection wraps to the first item, keeping its group label visible. Only `[data-slash-command]` buttons participate in keyboard selection. `applyLocaleToPanel` rerenders an open menu in the new language.

Composer controls draw [PanelIcons](../../extension/src/shared/panelIcons.js) line icons, the same 16-unit style as the panel header, instead of text glyphs. `ComposerPanel.create` receives the module through its `icons` option from the composition root. The run button contains both Send and Stop glyphs; its existing `data-action` attribute selects the visible one, so `setRunning/syncComposerSendAvailability` need no icon logic. Close buttons on toasts, context chips and attachment previews use the same `close` path (class `codex-close-glyph`): the runtime passes `icons` to `createComposerAttachmentController` and `createContextTrayController`, which fall back to a `×` text glyph only when no icon module is supplied. The settings workbench close button uses the settings `codexIcon('close')` path.
**Scope line above the composer.** `[data-probe-status]` (`.codex-probe-line`) shows only what Codex will read: `renderProbeStatusLine` in [contentRuntime](../../extension/src/content/contentRuntime.js) picks an icon and label through `getProbeScope` (Current file when the page exposes an editor, otherwise Selected files, Selected context or Whole project from the focus files), adds a "Refreshed:" prefix after a manual refresh, and appends the OT state when OT is enabled. Conditions the run resolves itself are not shown: `ensureReviewingBeforeWrite` switches Overleaf to Reviewing before the first write, and an editor that is not yet writable is reopened at write time; `formatProbeUserNotice` therefore reports these as ready. Only `renderProbeStatusMessage(..., 'warn')`, currently used for a failed manual refresh, adds the amber dot. `formatProbeStatusBar` keeps the full mode/readiness sentence for diagnostics and the diagnostics export.

**Unavailable Track.** `contentRuntime.renderProbeStatusLine` retains its scope label and appends a separate amber `data-tone="warn"` segment (“Track Changes unavailable” / “无法留痕”) when Track is checked and project memory is still fresh. `syncReviewingTooltip` updates both the checkbox and its label to explain that Codex asks before each run; the control stays enabled. A Track-off/manual-override probe notice describes untracked writing and does not claim Reviewing was confirmed.

`PanelRenderer.createConfirmController` accepts explicit `{value,label}` choices while preserving boolean results for existing callers. The preflight dialog offers continue for this run, disable Track for the active project session, and cancel. Escape, backdrop click, dialog close/removal and `REVIEWING_CONFIRM_TIMEOUT_MS` cancel the decision; an AbortSignal and original run/account/project predicate dismiss it on cancellation or navigation. Ownership is rechecked after a choice and before committing the effective policy. Affirmative choices still verify Editing before model dispatch. See [Track preflight](auto-edit-undo.md#4-auto-writeback-obtain-per-item-results-before-recording-recovery-evidence) and [project memory](run-state-and-recovery.md#31-execution-snapshots). DOM contract tests do not substitute for live Overleaf/browser acceptance.

When that dialog returns a declined choice under the original run ownership, `preflightWriteSafety` uses `failureReason_reviewing_unavailable_cancelled_next`: nothing ran, Track is unchanged, and sending again offers the choice. It identifies this case through the existing `reviewingUnavailablePreflight` flag and the absence of `resolveWritePolicy`'s affirmative `trackingDecision`; a failed Editing check after Continue/Disable keeps the ordinary guidance. The report stores the translated Next text, and `RunCompletionMeta` recognizes the bilingual key for both structured metadata and saved flat appendices. The `reviewing_unavailable` failure code and generic guidance remain unchanged for other paths, including writeback and recovery; no new persisted field is needed.

**Notifications and Native setup.** Runtime `showPluginToast` accepts `groupKey`, `groupItem`, `groupSummary` and an optional title. It merges into an existing toast with that key even when other notifications intervene, deduplicates items and updates the expandable summary without resetting its disclosure. Ungrouped notifications retain consecutive identical-text counting; the dismiss control, status styling, sticky lifetime and three-toast limit remain. [NativeCompatibilityController.notifyBlocked](../../extension/src/content/nativeCompatibilityController.js) supplies the missing-host group with a localized title and install/reload guidance, plus method names as `<code>` list items under a feature count. The method-specific error response and active-run event path remain separate from this toast presentation.

`NativeCompatibilityController.showUpdateGuidance` uses the same `.codex-plugin-confirm-head`, icon, brand and title structure as [PanelRenderer.createConfirmController](../../extension/src/content/panelRenderer.js). The composition root explicitly supplies `getIconUrl` from the same dialog-icon asset. The brand reads Codex Overleaf Link; `.codex-native-guidance-command` is a bordered monospace box, and `.codex-native-guidance-link` uses the accent token and a trailing external-link arrow. Their styles live in `panel.css`; installation identity and command resolution are unchanged.

**Type scale and colour tokens.** `panel.css` defines `--tl-text-xs/sm/md/base/lg` (11/12/13/14/15px) beside the motion tokens on `#codex-overleaf-panel`. Every panel text size at or below 15px uses one of them, written as `var(--tl-text-sm, 12px)` so dialogs rendered outside the panel keep a fallback; heading and display sizes from 16px up remain literal. New rules should use these tokens and the existing `--tl-*` colour tokens rather than raw hex values, so light and dark themes stay in step. In the light theme `--tl-review` is `#8a6508` (AA contrast for small text on white). ### History Viewing, Cleanup, and Result Actions

Creating, switching, renaming, and deleting individual sessions go through the header switcher ([SessionMenuView](../../extension/src/content/sessionMenuView.js)) and the PanelRenderer new-session button into `SessionManager`; see [header session switcher](#header-session-switcher). For empty-session reuse, capacity confirmation, manual titles, and resetting the final session, see [session lifecycle](run-state-and-recovery.md#session-lifecycle).

[PanelMaintenance.openChangeHistory](../../extension/src/content/panelMaintenance.js) opens settings, switches the workbench to the History page through the settings instance's `revealGroup('history')`, and delegates auditLogs/session reads to [ChangeHistoryView.load](../../extension/src/content/changeHistoryView.js). `openStorageSettings`, used by the storage-failure recovery action, reveals `storage` the same way. `revealGroup` returns null for a group that is unavailable in the current scope.
The latter captures the account, project, container, and request generation, then rechecks them after asynchronous completion. A timeout or read failure displays an error and retry entry point; failure must not be projected as no history. History rows jump to their owning session and run through runtime `jumpToHistoryRun`.

| Cleanup entry point | Actual owner and scope | Separate outcomes and limits |
| --- | --- | --- |
| Clear history in settings | `PanelMaintenance.clearAllHistoryWithConfirm` → `StorageDb.clearAllStores`, followed by project-name cache reset, session-state reconstruction, and save | Checks the current page's `currentRunView` and proceeds after destructive confirmation; this entry point does not call Native `codex.history.clearPlugin` |
| Cleanup implementation with shared history enabled | [SharedSessionBridge.decorate](../../extension/src/shared/sharedSessionBridge.js) delegates session cleanup to `erase('clear-account')` and deletes the current account's site-local legacy session backups | Other accounts' legacy backups remain. Auxiliary stores are cleared in one transaction through site-local `clearAuxiliaryStores`, advancing the attachment-draft epoch; their scope cannot be inferred from session account isolation |
| Legacy storage implementation | [StorageDb.clearAllStores](../../extension/src/shared/storageDb.js) empties `STORES` in a transaction in the current site's IndexedDB | This is a different storage boundary from the background shared account-session database; placing the control under the project settings filter does not narrow its scope |
| Per-project dashboard cleanup | [ProjectSessionCleanup.clearProjectSessions](../../extension/src/content/projectSessionCleanup.js) captures account, project, and dashboard render generation, queries owned sessions, checks running state, and asks for confirmation. After confirmation it rereads, then handles tombstones, compatibility blobs, shared deletion, and Native history cleanup | Processes only confirmed sessions that still exist; retains sessions added after confirmation and stops if a recent running record appears. Missing account or changed identity/view stops subsequent steps. Session deletion counts and Native cleanup failures are tracked separately |

Per-project cleanup buttons capture the account and dashboard render generation when created. Old buttons and views changed during confirmation cannot continue cleanup. Identity is rechecked before and after every asynchronous query and side effect. Compatibility-blob reads/writes receive the same guard; shared `deleteRecord` explicitly receives the expected account/project, followed by bridge capture and background-lock checks. Cancelled confirmation or invalidated identity does not display complete success.
This operation spans compatibility tombstones, old blobs, the shared database, and Native, and remains a stepwise cleanup. Guards prevent later actions; already completed or dispatched actions in the original scope cannot be rolled back together. When changing cleanup, use disposable history and check the captured account/project before and after confirmation.

After clearing storage, old session compatibility mirrors, drafts, and controller inputs are cleared together before a blank session is created. Complete-success feedback requires durable confirmation of the new state. Name-cache cleanup or save failure displays partial completion while the old in-memory state stays cleared. See [state after clearing history](run-state-and-recovery.md#clear-history-state).

Forking copies history from the selected node and creates a new Native thread. For source-thread priority, removal of Undo material, compensation after save failure, and persistence-field gaps, see [session forks and recovery-material isolation](run-state-and-recovery.md#61-session-forks-and-recovery-material-isolation).

### Submitted Input, Drafts During a Run, and Edit & Resend

New/switch session operations briefly protect the composer while the old draft's composition and durable save finish. [ComposerPanel.setSessionTransition](../../extension/src/content/composerPanel.js) keeps task text readable and preserves Cancel; `SessionManager.isTransitioning` guards sending, slash commands and queue promotion. Programmatic queue pull-back and Edit & resend check the read-only input before consuming their source or replacing text. Outside this transition, input during a model run remains editable. See [draft ownership and scheduling](run-state-and-recovery.md#composer-draft-persistence).

These three states resemble a letter already sent, a draft on the desk, and a letter waiting to be sent: a submitted run consumes its execution snapshot, new input in the current textarea writes the active session's `task`, and queued items retain their own text/payload. Locate each owner separately when a run ends, a session switches, or the view is redrawn.

```text
textarea input/compositionend → persistPanelInputs → captureComposerDraft → updateActiveSessionDraft → independent draft timer → existing save queue
submission → safeRunTask
  ├─ no current run: runTask captures input/ownership → flushes pending draft durably → waits for both skill catalogs as needed → waits for the old mirror → prepares Provider/style → startRunView → waits for audit and rechecks identity → conditionally clears input
  └─ current run exists: queueComposerInput → RunQueueScheduler coordinator → pendingInputs
result-card Edit & resend → refillComposerForRetry → prepareRetryReplacement → session draft
```

`SessionState.updateActiveSessionDraft` operates on normalized state. It changes only the active session's task, update time and existing automatic-title projection, then mirrors the task at the panel level. Manual titles, stable automatic titles and text sanitization retain their existing rules. Runs, events, history and queued-input objects retain their references; ordinary typing does not normalize the run collection or reread model, mode or attachment controls. An unchanged normalized task returns the original state, so repeated final input, `compositionend` and `change` events do not create another draft revision.

`captureComposerDraft` captures input-method composition updates immediately; [ComposerPanel](../../extension/src/content/composerPanel.js) also binds `compositionend` to capture the committed value when no final input event follows. It schedules persistence using `DRAFT_SAVE_DELAY_MS` and `DRAFT_SAVE_MAX_WAIT_MS` in runtime: an idle delay after the latest edit and a maximum interval before requesting a save during continuous typing. The independent timer joins the existing save queue when due and does not postpone other queued writes. A task `change` event, normally emitted after an edited textarea loses focus, flushes a pending draft. Page hiding and `pagehide` request best-effort flushing; browser teardown can interrupt asynchronous storage. SPA route changes snapshot a departing pending draft for a separate best-effort save under its original account/project, without reading destination attachments or writing fallback state there. Session transitions and non-queued submission use an awaited durable flush. See [draft persistence](run-state-and-recovery.md#composer-draft-persistence) for ownership, success and failure boundaries.

`syncComposerSendAvailability` in [contentRuntime](../../extension/src/content/contentRuntime.js) presents cancellation during a run when no text is entered, and queued submission when text exists. `safeRunTask` delegates submissions made during an active run to the queue coordinator.
`runTask` captures input, the submitting session, the prompt's session projection, the thread, and both sets of skill switches before its first await. Ordinary submissions share catalog preparation through `primeCodexOverleafSkillsCatalog/primeCodexLocalSkillsCatalog` according to the master switches, then derive enabled IDs from the captured per-item preferences. Missing local entries inherit the source's `enabled` value; explicit local invocation forces a refresh. An empty local catalog is valid. Read failure uses the existing task-start error notice and retains input; the task has not yet been dispatched. The flow then waits for `pendingMirror` and Provider/style preparation; the style snapshot is still acquired after loading. `startRunView` creates the record under the captured sessionId. `safeRunTask` uses a preparation flag to prevent duplicate starts.
After creating the run, the flow waits for the audit draft, then rechecks account/project identity and conditionally clears submitted input. New input is retained if the original session draft or current text, attachments, skills, or selection has changed. In-flight attachments and generation changes in `SelectionContextView.getRevision` also prevent clearing. After a session switch, only the original session's still-matching task may be cleared; the current composer is retained. Queue promotion skips this cleanup. Ordinary and skill-installer parameters consume the captured session projection; see [run state and recovery](run-state-and-recovery.md#31-execution-snapshots).
Runtime `buildCodexRunParams` passes `getLocale()` explicitly to [RunController.buildCodexRunParams](../../extension/src/content/runController.js), and `runSkillInstallerTask` sends the same current UI locale directly. Locale is read when parameters are built, including queue promotion and business retries; it is not frozen into `RunExecutionSnapshot`. For model reply guidance, Native uses `params.locale` as the fallback when the latest user request has no clear reply language. The background sanitizer preserves this field and `nativeQuotas` does not apply a field allowlist; a Native without the new prompt guidance can continue ignoring it. For stable rules versus dynamic prompt context, see [prompt materials](context-and-governance.md#stable-instructions-and-per-turn-materials).
An explicit local skill can still become unavailable during Native rediscovery after passing Content checks. `restoreRejectedLocalSkillSubmission` restores only a composer that this submission actually cleared, whose ownership is unchanged, and which the user has not since edited. Draft, selection, and attachment revisions jointly constrain late restoration. `ComposerAttachments.restoreSubmittedAttachments` restores in-memory attachments using the ordinary composer's count, per-item, and total-byte limits, including original attachments exceeding the refresh-draft budget. Separate persistent-draft limits remain unchanged. This recovery handles `codex_local_skill_unavailable`; it does not generally restore every failed task.
[PendingInputView.pullBack](../../extension/src/content/pendingInputView.js) refills only queued items. If a nonempty draft already exists, it displays a notice and returns. The callback performs actual queue removal and persistence; UI refill alone does not prove a transaction committed. For queue admission, advancement, and save boundaries, see [run state and recovery](run-state-and-recovery.md).

**Queue display and recovery entry points.** The `data-pending-inputs` container created by [ComposerPanel](../../extension/src/content/composerPanel.js) is hidden by default. `PendingInputView.render` shows it for a nonempty queue; paused items also display Queue paused and Resume. Switching to an empty queue clears old cards; switching back displays that session's queue again.

Rendering does not save, Resume, schedule tasks, or change draft/queue state. Maintenance here must check session loading, paused state after recovery, and DOM rendering together. When changing this path, reload a paused queue and check its visible cards without starting queued work.

**Follow-up guidance during a run.** After Steer is clicked in the queue, input that passes synchronous eligibility checks is immediately projected as a user bubble below the original user message and above the runtime execution details. Ordinary queued items remain in the queue above the composer. [RunGuidanceController](../../extension/src/content/runGuidanceController.js) owns the transient bubble; `getPendingGuidance` supplies an in-memory projection to the timeline, while the queue retains ownership and recovery material for this send. This projection is not saved as a delivered event.

[RunGuidanceView.reconcileGuidance](../../extension/src/content/runGuidanceView.js) merges confirmed events and in-flight projections into `data-run-guidance`, updating and deduplicating by message ID in place. Real sends with identical text but different IDs remain distinct; old records without IDs retain existing compatibility rules. [RunActivitySummary](../../extension/src/content/runActivitySummary.js) separates guidance from runtime display blocks; the path without an activity presenter in [RunTimelineView](../../extension/src/content/runTimelineView.js) uses the same projection method. Activity updates, history redraws, run completion, and cancellation all use this region; collapsing execution details does not hide user input. Language changes redraw product-generated labels while preserving user text. If a long expanded execution view requires leaving the bottom, auto-follow is temporarily disabled and `.run-guidance-text` maintains a reading anchor. The existing latest button restores following, and runtime expansion remains unchanged. If the user is already reading history, or begins scrolling upward before the next frame is drawn, reading position is not moved proactively. Scrolling affects only the extension panel. A single oversized input prioritizes showing its beginning; the rest is available by scrolling the panel. Check the affected scrolling behavior through real wheel and send interactions when changing this path.

Tool status within execution details is determined by individual events. `RunActivitySummary.effectiveState` displays “Result unconfirmed” when the entire run has ended but a tool still has only `running/pending` evidence. Run completion does not fabricate success for each tool. Diagnosis must check Native notifications, `AgentTranscript` mapping, and thread/turn/item identity merging in `RunActivityModel`.

When changing Steer presentation, submit one follow-up during a running task and verify its immediate placement above runtime, confirmation in place, and persistence after refresh. Check the changed failure/locale path as applicable; these UI paths have no retained automated release test.

[RunTimelineView.configureEditButton](../../extension/src/content/runTimelineView.js) offers Edit & resend for cancelled/rejected records that pass `canEditRun`; the button is disabled while a current run exists.
[PanelMaintenance.refillComposerForRetry](../../extension/src/content/panelMaintenance.js) refills the task and calls runtime `prepareRetryReplacement`. ## 5. Selections, File Context, and Attachments

### Selection References and Selection Editing

[SelectionContextView.attach](../../extension/src/content/selectionContextView.js) captures projectId, sessionId, and generation, then rechecks ownership after `getSelectionContext` and after opening the composer.
[SelectionContext.normalize](../../extension/src/shared/selectionContext.js) validates project-relative paths, nonempty text, ranges, and document hashes; `MAX_TEXT=20000` is measured using JavaScript string length.
Selection paths use complete literal project paths up to 2048 characters, without truncating them into aliases. Invalid paths containing backslashes, control characters, or leading/trailing whitespace are rejected. Page checks the document and selection for isolated UTF-16 surrogate code units to prevent UTF-8 replacement from invalidating hash assumptions; complete emoji remain valid selection content.
Ranges satisfy \(0\le from<to\) and \(to-from=|text|\), and carry `documentHash` to identify the source document version.
`reference` mode attaches reference content. `edit` mode displays “Selection only,” and runtime `setSelection` also sets the session mode to Auto. Actual restrictions on localized editing also depend on [selectionScope](../../native-host/src/selectionScope.js); the label itself provides no execution guarantee.
Native `prepareSelectionScope` checks the whole-document SHA-256 and selected text after mirror synchronization or reuse preparation and before executor startup. Optional `rebaseEvidence` captured by Page also stores SHA-256 values for the entire prefix and suffix, plus document length. Coordinates and lengths use JavaScript UTF-16 code units; full prefix/suffix text is not persisted.
When the whole-document version changes, relocation is allowed only if the selected text is unchanged and one complete side still matches. Let the old range be \([f,t)\), old length \(L\), new length \(N\), and selection length \(m=t-f\). Candidate starts are the original position \(f\), or \(N-(L-t)-m\), derived from the old suffix relative to the document end. The former requires the complete prefix hash to match, the latter the complete suffix hash, and exactly one valid candidate must remain after deduplication. Changes on both sides, changed selection text, or multiple valid positions cause rejection with `selected_context_unresolved`. Old records without this evidence continue using strict whole-document version checks. After relocation, coordinates, line numbers, documentHash, and model input all use the current document version.
`filterSelectionChanges` retains valid text writes to the same selection path individually: `previousContent` must equal the current baseline, and the result must satisfy \(after=prefix+replacement+suffix\). Cross-file, structural, or binary operations and text changes outside the selection become `selection_scope_violation`; duplicate results for the same path are rejected. A mixed out-of-scope change within one file is rejected as a whole when separability cannot be proved. Content includes rejected items in skipped/blocked; mixed results explicitly show partial completion and retain Undo for the written portion. The local mirror may remain dirty.
Remote changes after startup are still checked by the Page stale guard; startup relocation does not automatically resolve them. Reference mode does not enable edit-only filtering. When changing selection editing, verify the captured range and submitted intent, then check that a proposed edit outside that range leaves the document unchanged.

After sending, `renderSent` renders the chip from the run execution snapshot; removing selection from a draft must not delete the historical chip. Page selection probing also checks editor focus, connection state, and probe generation.

### Multiple Attachments: Asynchrony, Budgets, and Recovery

[ComposerAttachments.createComposerAttachmentController](../../extension/src/content/composerAttachments.js) receives paste/drop/file input, deduplicates and reserves budget, then waits for FileReader and image previews.
`pendingAttachmentKeys` prevents concurrent duplicate reads of the same file. The budget includes completed and pending bytes in the current composer generation; only a `finally` in that generation can release the reservation. This prevents an old read from subtracting a new batch's budget or removing a new reservation for the same file.
`addFiles` processes a batch sequentially. A validation/read exception stops later files and reports failure through the original entry point while retaining the accepted prefix. The batch's final `finally` redraws only for the current generation. Internal lists and the tray therefore remain consistent across success, failure after partial acceptance, count limits, and insufficient total budget. Cleared old batches do not redraw new input.
When changing batch import, use valid files around one unreadable or oversized file and observe which files remain eligible for sending; a failure does not imply rollback of the whole batch.

The ordinary composer's admission configuration comes from the runtime: \(n\le8\), each \(b_i\le12\,\mathrm{MiB}\), and \(\sum b_i\le32\,\mathrm{MiB}\). Empty attachments are rejected; this differs from the semantics of valid empty project files.
**Clearing and in-flight reads.** Each `addFiles` captures `attachmentGeneration` and rechecks it in the batch loop, after FileReader completion, and after preview completion. `clear` increments the generation and clears attachments, reserved keys, and bytes, allowing immediate admission of a new batch. Old read results, remaining files in old batches, and old-generation errors become invalid and cannot reenter outgoing input. Old `finally` handlers do not change new-generation reservations. The underlying FileReader/Image operations are not forcibly aborted; they may finish and have their results discarded. The current budget therefore constrains valid composer content and reservations, without providing a combined memory cap for all historical in-flight I/O.
When changing asynchronous attachment reads, clear or switch the draft while a read is pending and verify that late bytes cannot reappear in the submitted task.
[NativeQuotas](../../native-host/src/nativeQuotas.js) retains per-item/count constraints for ordinary attachments, with an aggregate limit of 96 MiB. Native's broader limit does not establish what the UI accepts. Writing-style references use a separate quota set.
`getAttachmentsForRun` includes the content for the current send. `createRunAttachmentSnapshots` retains only names, types, sizes, and bounded previews, avoiding copies of complete attachments in history cards.
`serializePersistableAttachments/restorePersistedAttachments` provides serialization/refill helpers: at most three items, each with `contentBase64.length <= 1,048,576`, measured in Base64 characters.
Base64 length is approximately \(4\lceil B/3\rceil\), so this character threshold is not a 1 MiB limit on raw file size. Attachments exceeding recovery limits can still participate in the current submission but are not saved as refreshable drafts.

**Attachment-draft persistence.** [ComposerAttachmentDraft](../../extension/src/shared/composerAttachmentDraft.js) manages a separate account/project draft in the current site's IndexedDB `artifacts` store. Complete attachments do not enter global prefs, shared session records, or compact fallback. It preserves project-composer ownership; switching sessions in the same project does not automatically change attachments. Cross-origin shared sessions between www and cn do not include this site-local attachment draft.
`ComposerAttachments` add/remove/clear operations update memory and schedule saving through `onChange`. Runtime `saveState` calls `getComposerDraftPersistence().save` within the captured-scope transaction and writes only attachments that actually changed. In [contentRuntime.js](../../extension/src/content/contentRuntime.js), `loadStoredStateForProject → loadComposerAttachmentsForProject` loads the account/project draft into `state.composerAttachments`; `applyStateToPanel` then restores it through `getComposerDraftPersistence().hydrate`. Ordinary attachment-read I/O failure reports attachment unavailability without discarding already loaded session history; identity or load-generation mismatch still rejects the result.
`syncScope` clears the controller and invalidates old FileReader work when the project or account changes. Scope generations and read sequence numbers prevent old asynchronous results from overwriting a new draft. `hydrate` initializes each scope only once; local additions, removals, or clearing take precedence over late recovery.
Draft writes compare revision and cleanup epoch within the same IndexedDB transaction and commit only if they match. A conflict rejects stale writes and explains recovery. Clearing history atomically clears auxiliary stores and advances the epoch. Edits that have not yet acquired an initial version additionally check the time of the first change; a failed save retry cannot use a freshly read version to resurrect pre-cleanup attachments. This mechanism protects concurrent writes without automatically projecting another tab's attachments into the current UI in real time.
When changing attachment recovery, check the actual save/load route and a Chrome refresh. Normalization support alone does not establish that the persistence caller writes attachments.

`runTask` captures completed attachments before asynchronous Provider/style loading and clears the composer after creating the run. The queue coordinator rejects queued input with attachments; see [RunQueueScheduler](../../extension/src/content/runQueueScheduler.js).
Submission captures only attachments already complete at that time, without waiting for in-flight reads; clearing invalidates old-generation reads. The complete submission interaction and real browser sending still require acceptance; see section 9.

[LineReferences.parseLineReferencesFromText](../../extension/src/shared/lineReferences.js) recognizes single positions and inclusive ranges: `path:START-END` (hyphen or en dash), `path line START-END` / `path lines START-END`, and `path 第START-END行` / `path 第START至END行`. Markdown link targets also accept colon ranges. Positive integer endpoints must satisfy `START <= END`; equal endpoints become a single-line reference, and mixed column ranges such as `path:12-20:5` are rejected. Path resolution still requires a recognized project text file and rejects unsafe path segments.
`.codex-line-reference` renders as a quiet monospace pill (accent wash, solid accent on hover/focus). Range pills display `path:START–END`, expose `data-end-line`, and carry `line`, `endLine`, and `selectLine:true` to Page `jumpToPosition`. [textCoordinates.resolveJumpToPositionRange](../../extension/src/page/textCoordinates.js) ignores column for a supplied `endLine` and selects from the start of `line` through the end of the requested last line, clamping that last line to the document's line count. An out-of-range start or an invalid/reversed end returns `line_out_of_range`. The Page dispatcher forwards the complete parameters; its identity policy is unchanged, and Page closure changes require updating `pageRpcContract.REVISION` as described in section 1.
The surrounding text, including parentheses, is kept verbatim. `groupLineReferenceNodes` moves an immediately preceding `(` text character and a single-line or range pill into `.codex-line-reference-group`. Both `buildLineReferenceInlineNodes` and the general inline assembly apply it, covering plain references, `buildMarkdownLinkNodes` and supported inline-code references; `renderMarkdownBlockText` also groups adjacent text/link tokens after the main DOM renderer. `MarkdownText.buildInlineCodeNodes` converts a token containing exactly one project position or range into one pill, forwarding `endLine` for ranges; mixed text and invalid ranges stay code. The main renderer uses this callback for standalone code spans but retains embedded inline code as code. Scoped CSS keeps the group and its pill on one line despite the general `.col-log` wrapping rule. The transformation preserves text and click handlers, so grouping does not alter `innerText` copying or navigation parameters.
For a cross-file jump, [pageBridge.jumpToPosition/waitForActiveEditorAfterNavigation](../../extension/src/pageBridge.js) waits for the target path and usable editor text before resolving offsets. When both captured identities expose a CodeMirror view, the document object must change: a new view or `EditorState` with the old document is insufficient, since file-tree activation can change focus or configuration before the target text loads. Other editor types retain the existing surface-identity fallback. Same-file jumps use `treeOperations.waitForActiveEditorText`. This navigation-only check leaves the shared identity helper and writeback/Undo guards unchanged. Verify the first click from another file, including a range beyond the old file's length and one valid in both files; neither case may select the old document. Actual Overleaf acceptance is required to verify its editor lifecycle.
Native [codexPromptAssembly.formatProjectLocationCitationRules](../../native-host/src/codexPromptAssembly.js) instructs the model to use project-relative `path:LINE[:COLUMN]` for positions and `path:START-END` for spans. These rules are part of `buildCodexDeveloperInstructions`, apply to files in the workspace rather than only selected focus files, and retain plain-text citation, local-path exclusion, and uncertain-line guidance.
[LineReferences](../../extension/src/shared/lineReferences.js) and MarkdownText sanitizers clean local paths while retaining range endpoints when replacing a local reference with a project path or placeholder. New text, code, href, or diagnostic fields must each have their corresponding path checked. The presence of sanitization does not establish that every future input is free of leakage.

## 7. Actual Entry Points for Diagnostics and Popup

[DiagnosticsController.runAllDiagnostics](../../extension/src/content/diagnosticsController.js) sequentially collects Native, page, snapshot, and OT checks and aggregates the worst health. DiagnosticsPanel owns menus, loading, and result DOM. `DiagnosticsPanel.create/bindStaticActions` places `[data-refresh]` first in the health menu with the refresh icon supplied through `icons: Modules.PanelIcons` and localized `refreshProbeTitle/refreshProbeSubtitle` text. Selecting it closes the menu and calls `callbacks.onRefresh`, wired by `ensurePanelOpen` to `refreshProbe({ userInitiated: true })`. This re-reads Overleaf state without syncing or modifying files. Runtime `setRefreshProbeLoading` owns disabled, `data-loading`, `aria-busy` and localized title/ARIA state on the menu item; only its icon spins. `applyLocaleToPanel` and `DiagnosticsPanel.refreshLocale` update the item text while preserving loading state. PanelRenderer no longer renders or binds a header Refresh action.
`DiagnosticsController.refreshLocale` rebuilds display from observations already obtained for the current request without rerunning checks. `DiagnosticsPanel.refreshLocale` preserves dismissal, expansion, and scroll position; technical evidence remains the original result. Request generations and account/project/route constraints still apply. When changing this path, switch language while results are open and verify that no check is restarted.
[DiagnosticsPanel.closeResult](../../extension/src/content/diagnosticsPanel.js) hides results and sets `resultDismissed`. `showResult` ignores results while this boolean barrier is true. The close button, Escape, and outside clicks can all enter this path. Closing does not cancel the underlying checks; a full check may continue and update health.
Each visible full or individual check creates a new request generation through `DiagnosticsController.beginDiagnostics`, capturing account, project, and route generation. Only a still-matching request may publish results; full-check health updates use the same guard. Internal `collectOnly` subchecks reuse their parent request and do not compete for visible results. After a later `showLoading` clears `resultDismissed`, an old check still cannot overwrite the new one. If the result was merely closed and no new check started, the original check may still update health. This mechanism filters late results without cancelling already dispatched underlying reads.
When changing diagnostics, start a check, close or replace its result, and verify that its delayed completion cannot overwrite a newer result or a different project. Check layout only on the surfaces affected by the change.
[DiagnosticsExport.exportDiagnosticsBundle](../../extension/src/content/diagnosticsExport.js) collects recent run, audit, mirror, and Native summaries. After asynchronous collection, it rechecks projectId and passes them to [AuditRecords.buildDiagnosticBundle](../../extension/src/shared/auditRecords.js).
The audit writer retains the run's account. Export queries first read by projectId, then filter by the captured account, and recheck account/project after collection. Old audits without an account are excluded from export. For legacy run-summary field compatibility, history filtering, and deletion scope, see [audit and diagnostic consumption](context-and-governance.md#5-audit-and-diagnostics-consumers); identity guarantees must be assessed separately for each source.
AuditRecords builds summary fields and applies secret-like text handling. The maintenance constraint is to keep body content, complete attachments, and credentials out of diagnostics. New fields must be traced through collection, summarization, and export; handling of existing fields does not guarantee that other outputs cannot leak.
[Direct popup HTML](../../extension/popup.html) and [Managed popup HTML](../../extension/bootstrap/popup.html) share [src/popup.js](../../extension/src/popup.js); the latter loads replaceable code and CSS through runtime paths.
`ensureMinimalPopupShell` can adapt old Managed HTML shells. `initPopupState/applyPopupPreferences` reads global locale/theme, listens for changes, and sets `<html lang>`.
Popup product-generated dynamic statuses, copy feedback, and site-authorization explanations redraw with the language. Managed repair guidance continues using the original installation identity and platform; language changes do not request permissions again. Managed HTML first loads the fixed [popupFallback.js](../../extension/bootstrap/popupFallback.js), so existing repair guidance can read the language preference even when the runtime cannot load. This script updates only a fallback shell that still exists; late callbacks after normal runtime shell replacement do not overwrite the UI. This fixed asset is delivered by a full Managed installation or an explicitly declared compatible Bootstrap migration; replacing runtime alone does not update it. See [installation boundaries](installation-and-updates.md#9-manual-upgrades-and-bootstrap-boundaries). When changing this shell, verify its visible language with the runtime unavailable.
The launcher switch first reads `get-panel-state`, sends `toggle-launcher` as needed, and reads back for verification. It controls only side-launcher visibility; panel opening/closing has separate actions.
The current Managed HTML does not reference [bootstrap/popup.js](../../extension/bootstrap/popup.js); [contentScript.js](../../extension/src/contentScript.js) is also absent from the current canonical content entry. The existence of old files and current execution are separate kinds of evidence.

## 8. Minimal Change Recipes and Validation Routes

| Change intent | Minimum coordinated path | Change-driven verification |
| --- | --- | --- |
| New content controller | Source import → registry dependencies → legacy adapter if needed → runtime callbacks/getters → bundle | Build the production content entry and mount it in Chrome; missing imports and unresolved runtime dependencies have different failure points. |
| New MAIN method | Implementation → RPC catalog → WAR → PageBridgeClient ordering → dispatcher/capability → consumers | Invoke the changed method through its real dispatcher; check rejected identity and duplicate delivery when it mutates documents. |
| Setting or layout | Field owner → SettingsPanel read/load → coordinator → Workbench mapping → i18n/CSS | Change the setting, reopen its panel, and refresh; inspect only the affected layout and locale. |
| Timeline scrolling, latest button, or redraw position | RunTimelineView follow intent/frame scheduling → RunScrollLayout reading anchors → history redraw options/CSS | Use a long answer and real wheel/keyboard input; preserve the visible paragraph through the changed redraw. |
| History viewing or cleanup | PanelMaintenance / ChangeHistoryView → shared/legacy storage scope → ProjectSessionCleanup / Native → redraw | Use disposable sessions; confirm the intended account/project and check the result after refresh. |
| Drafts, Edit & resend, or queue refill | textarea / RunTimelineView → PanelMaintenance → runtime / RunController → session or queue owner | Keep a later draft present and observe which task is actually submitted or restored. |
| Result-card fork | RunResultActions → SessionForkController → [Native thread fork](../../native-host/src/codexThreadFork.js) → record copying / saving / compensation | Fork a disposable run and refresh; verify copied history and disabled original write actions. |
| Model or selection input | Request identity/capability → view → state → execution snapshot → Native consumers | Observe the actual submitted model/selection after the changed asynchronous interaction. |
| Attachment/output display | Input budget/recovery or renderer → consumers → CSS/resources → failure fallback | Exercise the changed attachment or renderer path and its relevant failure with real browser input. |
| Activity card or post-write receipt | AgentTranscript / RunActivityModel → RunTimelineView / RunActivitySummary; writeback → WrittenChangesView | Compare one live result and its reloaded display with the underlying saved facts. |
| Popup/diagnostics | Both HTML shells → shared runtime → preference/state reads → summary fields | Open the affected shell/result, change locale if relevant, and verify late-result ownership. |

Do not append source scripts for new Content modules to either manifest; [build-content-bundle](../../scripts/build-content-bundle.mjs) generates the output. New Page scripts require a separate WAR check; a content import cannot load MAIN capabilities.
New settings must define defaults, scope, migration, failure presentation, and listener destruction. New visual proxy controls must retain existing persistence-event entry points.
Choose verification for the changed path from the table; this is not a full release matrix. Most presentation behavior has no permanent automated test. The retained core protects document integrity, recovery, and selected-language report projection through production modules with external I/O substitutes.

```sh
# Run the retained report-projection contract when changing conclusions.
node scripts/run-tests.mjs test/reportConclusionLocale.test.js
# Rebuild the actual content entry after loading/composition changes.
npm run build:content
```

[run-tests.mjs](../../scripts/run-tests.mjs) selects files for execution; tests may create isolated temporary fixtures. Building proves source assembly, while the short Chrome acceptance checks runtime mounting. Add focused browser checks only for the changed surfaces, using real pointer/keyboard input where event order matters. Browser substitutes cannot establish actual Overleaf writeback.

## 9. Boundary Cases and Validation Points

Use these boundaries to select checks for the affected change; they are not additional routine release gates.

1. **Loading new scripts.** Content code cannot enter the actual application without entry imports or composition dependencies. MAIN modules still require injection and dispatch even when exposed as WAR. Check the execution chain rather than merely searching for a file's existence.
2. **Settings sections and persistence scope.** The workbench only places visible groups. preloadProjectContext is global, while Track writes through the active session. Scope changes must change owners and migration, beyond moving DOM.
3. **Late model-catalog responses.** Generation/provider/revision guards ignore late responses. A retained unverified fallback selection also does not establish verified service support. Test slow responses arriving after fast ones and custom Providers without catalogs.
4. **Attachment clearing and submission timing.** Controller generations prevent old reads, previews, and remaining batch items from reentering input; section 5 describes the change-driven verification path. Runtime submission still captures only completed attachments, and send availability does not wait for pending bytes. Real-browser validation must separately cover submission during reads, explicit clearing, and importing a new batch. Controller invalidation guarantees do not establish that the current task received every attachment.
5. **Resource limits in main and fallback rich-text paths.** Synchronous diagnostic exceptions are isolated. Very long Markdown, malicious links, and complex formulas still require separate validation of actual resource and presentation boundaries in main and compatibility paths. Main-renderer parameters do not establish identical limits across all fallback paths.
6. **Modals and loaded copies in the real browser.** Native-dialog top-layer behavior, focus restoration, fonts, and old Managed shells depend on Chrome and page state. Validation must cover mounting, keyboard use, closing, and reloading in the real browser.
7. **Attachment serialization and refresh recovery.** Although attachments pass through SessionState normalize/compact, actual prefs/session writes and hydration do not carry that field. Validate the complete save/load route described in section 5.

Target contract: controller destruction, asynchronous clearing/switching, and invalidated responses must preserve ownership identity. Rendering and diagnostic boundaries must be checked whenever fields are added. These targets do not establish that uncovered branches already satisfy them.
